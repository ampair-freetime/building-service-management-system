# G6, G8, G7 — การเปลี่ยนแปลงและวิธีตรวจ

## ก่อนเปิดใช้

รัน migration ของฐานข้อมูลก่อนเริ่ม Backend เวอร์ชันใหม่:

```sh
cd Backend
uv run alembic upgrade head
```

ถ้าใช้ Docker Compose ให้ build image ที่รวมโค้ดใหม่ แล้วรัน `docker compose run --rm backend alembic upgrade head` ก่อนเริ่มบริการเวอร์ชันใหม่

Migration `20261008_0021` เพิ่ม `claim_code` และ `staff_message` ให้ `lost_claims` เติมรหัสให้ข้อมูลเก่าตามวันที่สร้างในเวลาไทย แล้วบังคับไม่ให้ว่างหรือซ้ำ หากรหัสสั้นของแถวเก่าชนกันจะเติมเลขท้ายเพื่อรักษาข้อมูลทั้งสองแถว การทดสอบ migration ใช้ตารางชั่วคราวแยกจากข้อมูลระบบ หลังทดสอบผ่านได้รัน migration กับฐานข้อมูล Docker สำหรับพัฒนาของโปรเจกต์นี้แล้ว; หากนำโค้ดไปใช้กับฐานข้อมูลอื่นยังต้องรัน migration

## G6: ปิดงานพร้อมรายงาน

ภาพรวม: เจ้าหน้าที่กรอกรายงาน → Backend ตรวจสิทธิ์และสถานะ → เตรียม/อัปโหลดรูป → บันทึกสถานะ รายงาน รูป และเวลาปิดงานพร้อมกัน

- `Frontend/src/view-logic/useStaffDashboard.js` เปิดฟอร์มปิดงานเฉพาะงานที่กำลังดำเนินการ ส่งรายงานรวมไม่เกิน 2,000 ตัวอักษร และกันกดซ้ำขณะส่ง
- `housekeeperAPI.js` / `technicianAPI.js` ส่ง `FormData` ไป `POST /cleaning-tasks/{id}/complete` หรือ `POST /repair-requests/{id}/complete` โดยใช้ช่อง `note` และ `image` (รูปไม่บังคับ)
- `Backend/app/services/task_completion.py` ใช้ row lock (ล็อกแถวงานระหว่างบันทึกเพื่อกันการเปลี่ยนพร้อมกัน) และ transaction (บันทึกการเปลี่ยนแปลงเป็นชุดเดียว) เจ้าหน้าที่ต้องเป็นผู้รับผิดชอบและงานต้องอยู่ `in_progress`
- รูปผิดหรืออัปโหลดล้มเหลว: ไม่เปลี่ยนสถานะ ไม่สร้างรายงาน และพยายามลบรูปที่อัปโหลดไปแล้ว ถ้าลบคืนไม่สำเร็จจะบันทึก log
- `PATCH /status` ปิดงานไม่ได้อีก ส่วน `PATCH /repair-requests/{id}/complete` เดิมยังรองรับ แต่ต้องส่งรายงานด้วย
- งานเก่าที่ `completed` แต่ไม่มีรายงานมีปุ่มเติมรายงาน โดยยังใช้ endpoint เพิ่ม note/รูปเดิมได้ ไม่แก้สถานะย้อนหลังอัตโนมัติ

ลองตรวจ: ปิดงานพร้อมรูปที่ถูกต้องแล้ว refresh; ลองรูปเสียแล้วตรวจว่างานยัง `in_progress`; ลองปิดงานของคนอื่นต้องได้ 403; ลองส่งซ้ำหลังปิดแล้วต้องได้ 409

## G8: รหัสคำขอและการติดตาม

ภาพรวม: Guest ยื่นคำขอ → ได้ `CLM-YYYYMMDD-XXXXXXXX` → กรอกรหัสและอีเมลในหน้าติดตาม → เห็นผลตรวจหรือวันนัด → ส่งหลักฐานเพิ่มได้เมื่อเจ้าหน้าที่ร้องขอ

- UUID ยังเป็นรหัสภายในสำหรับ API ของ Staff ส่วนหน้าจอใช้ `claim_code`
- `GET /guest/claims/{claim_code}?claimant_email=...` คืนสถานะและข้อความที่ Guest เห็นได้ อีเมลผิดหรือรหัสไม่พบตอบ 404 เหมือนกัน
- `POST /guest/claims/{claim_code}/additional-info` รับ `{claimant_email, proof_detail}` ตรวจว่ารอข้อมูลเพิ่มอยู่ ต่อหลักฐานไว้กับข้อมูลเดิม แล้วเปลี่ยนเป็น `pending` ให้ Clerk ตรวจต่อ
- `staff_message` แยกจาก `review_note` ที่เป็นโน้ตภายใน ข้อมูลลับของสิ่งของไม่ถูกส่งออกให้ Guest
- จุดรับของและรายละเอียดนัดเปิดเผยเฉพาะคำขอที่ผ่านการตรวจ (`approved`, `scheduled`, `completed`)
- อีเมลนัดรับใช้ชื่อสิ่งของและรหัส `CLM-…` แทนรหัสสิ่งของ การส่งอีเมลยังใช้เส้นทางเดิมแบบรอผล เพราะการย้ายอีเมลเป็น background อยู่ใน G1
- URL ติดตามแบบ UUID เดิมยังใช้งานได้ช่วงเปลี่ยนผ่าน

ลองตรวจ: ยื่น → ขอข้อมูลเพิ่มจากหน้า Clerk → Guest ตอบ → Clerk อนุมัติ/นัดรับ → Guest refresh แล้วเห็นนัด; ทดสอบอีเมลผิด และคำขอที่ถูกปฏิเสธ

## G7: ข้อมูล Guest และ Clerk

- `lost-found-mappers.js` แยก `place` (สถานที่พบ), `evidence` (หลักฐาน), `reportedAt` (เวลารายงาน), `custodyLocation` (จุดรับฝาก), `activityLabel` (กิจกรรม) เพื่อไม่ใช้ field เดียวแทนข้อมูลหลายความหมาย
- แบบฟอร์มของหาย/พบของเลือก `location_id` จากสถานที่จริงได้โดยไม่บังคับ และยังระบุ `location_detail` เพิ่มได้
- เอาช่องจุดรับฝากจาก Guest ออก Backend เป็นผู้ตั้งค่าจาก `DEFAULT_CUSTODY_LOCATION`; ข้อความในฟอร์มอ่านค่าเดียวกันจาก `GET /guest/found-items/config`
- ปุ่ม “ฉันพบของชิ้นนี้” เปิดฟอร์มแจ้งพบของ เติมชื่อ/ประเภทและรหัสประกาศเดิมในรายละเอียด ผู้ใช้ต้องตรวจข้อมูลและกดส่งเอง
- เอาฟอร์มรับฝากของ Clerk/Admin ที่เคยเก็บแค่ในเบราว์เซอร์ออก ทางลัดเดิมเปิดรายการของที่รับฝาก
- คง `expires_at`, `archived_at`, `deleted_at` ไว้เพื่อรองรับ retention (การจัดการข้อมูลตามอายุ) ใน G5; รอบนี้ยังไม่มีงานลบหรือหมดอายุอัตโนมัติ และค่า NULL ไม่ได้หมายความว่าระบบทำงานผิด

## ชุดตรวจอัตโนมัติ

```sh
cd Backend
uv run pytest -q
# เพิ่มการทดสอบ migration กับ PostgreSQL container ที่กำลังรัน:
TEST_POSTGRES_CONTAINER=building-service-management-system-database-1 uv run pytest -q tests/test_claim_code_migration.py
cd ../Frontend
node --test tests/*.test.js
npm run build
```
